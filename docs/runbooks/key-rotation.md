# Key and secret rotation

Spec 12.5 (a rotation runbook for every secret type). Secrets live in the secrets manager (or OpenBao where the region needs it), fetched at startup; never in Git. Rotate on schedule and immediately after any suspected exposure (`incident-response.md`).

| Secret                                                                            | Where used                                                          | Schedule                                                                     | How                                                                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Service-token keys (Ed25519): `bff-patient`, `bff-clinic`                         | BFF signs, API verifies (`API_*_PUBLIC_KEY_JWK`)                    | 90 days                                                                      | 1. Generate a new pair. 2. Add the new public key next to the old one in the API's trust list (the verifier accepts per issuer; deploy). 3. Switch the BFF to the new private key (deploy). 4. Remove the old public key after 2 minutes (tokens live 60 seconds). |
| Workload keys: `api`, `jobs`, `bff-patient`, `bff-clinic`, `identity`, `keycloak` | Service to service (ADR-0018)                                       | 90 days                                                                      | Same pattern on the receiving service's trusted list (`IDENTITY_TRUSTED_*`, `API_*_WORKLOAD_PUBLIC_KEY_JWK`).                                                                                                                                                      |
| Rule set signing key                                                              | `tools/sign-ruleset.mjs`; API verifies (`ENDO_RULESET_PUBLIC_KEYS`) | Yearly, or on clinical-lead change                                           | Add the new key id to `ENDO_RULESET_PUBLIC_KEYS`, re-sign the rule set with it, deploy, then remove the old key id.                                                                                                                                                |
| VAPID key (push)                                                                  | API (`API_VAPID_PRIVATE_KEY_JWK`), BFF public key                   | Yearly                                                                       | Rotating invalidates subscriptions: publish the new public key, keep sending with the old key for 30 days while the app re-subscribes, then switch.                                                                                                                |
| KMS keys (`kms/clinical`, `kms/identity`, `kms/backup`)                           | Wrap per-patient and per-person data keys; backups                  | Automatic yearly key rotation in the KMS                                     | Old versions stay for decryption; no data rewrite needed. Never delete a KMS key version: shredding is per patient, by deleting her wrapped key.                                                                                                                   |
| Backup encryption key                                                             | `tools/backup.mjs`                                                  | With `kms/backup`                                                            | New backups use the new key; keep the old key until the last backup it protects expires (35 days).                                                                                                                                                                 |
| Database credentials (each role)                                                  | Services, relays, jobs, backup                                      | 90 days, or managed rotation                                                 | Create the new login in the same role, deploy, drop the old login.                                                                                                                                                                                                 |
| Keycloak client secrets and SMTP                                                  | Keycloak, BFF OIDC clients                                          | 90 days                                                                      | Regenerate in Keycloak, update the secret, restart the BFF.                                                                                                                                                                                                        |
| Keycloak realm signing keys                                                       | ID tokens                                                           | Keycloak key rotation (add a new active key, keep the old passive for 1 day) | The BFFs read the JWKS URL; no deploy needed.                                                                                                                                                                                                                      |

After every rotation: confirm sign-in, a check-in, a review decision and an audit write in staging, then production. Record the rotation (date, secret type, who) in the access review.
